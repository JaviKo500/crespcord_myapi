# Service request transaction timeline (back office)

Adds, to the native `node/%nid/edit` form of a `service_request`, a read-only
timeline of its `service_transaction` history plus the three actions an
operator needs over it: create, edit and delete. It is a page enhancement for
the operator, not an API endpoint — it returns HTML, never the JSON envelope,
and **no endpoint under `api/v1/` is involved or changed by it** (SPEC 94).

It depends on SPEC 77 (the `service_transaction` bundle, its four fields and
the `myapi_services_request_statuses()` catalogue), SPEC 92 (the automatic
initial transaction and the autogenerated title) and SPEC 49
(`myapi_building_admin_field_value()` / `_field_target_id()`, reused as-is to
read fields).

There is **no listing of its own**. Transactions are only ever seen inside
their request. `admin/content/service-requests` does not exist and is another
spec.

| File | Role |
|------|------|
| `myapi.module` | Two `hook_menu()` entries, the two access callbacks, `myapi_form_service_request_node_form_alter()` and `myapi_form_service_transaction_node_form_alter()` (glue only, both delegate), and the `'service_transaction'` branches of `myapi_node_insert()` / `myapi_node_update()`. |
| `includes/myapi.service_transaction_admin.inc` | Everything else: the timeline query and its render, the "Editar" and "Borrar" links and their access checks, the creation form with its validation and submit, the deletion confirmation form with its submit, both page callbacks, the two form alters with the redirect handler, and the status sync. Loaded by the `file` key of the menu entries and by `module_load_include()` from `myapi.module`. |
| `includes/myapi.service_transaction.inc` | **Not modified by this feature except its docblock.** It stays what SPEC 92 made it — the automatic initial transaction and the autogenerated title, code that runs inside every `node_save()` of the site. The `_admin` suffix is the whole distinction between the two files. |
| `includes/myapi.services_common.inc` | Reused, not duplicated: `myapi_services_request_statuses()` is the single source of the `select`'s options and of the table's status labels, the same one `myapi.install` reads to build `field_request_status`' `allowed_values`. |
| `includes/myapi.building_admin.inc` | Reused, not duplicated: `myapi_building_admin_field_value()` / `_field_target_id()` (SPEC 49) back the status sync, the redirect handler and the deletion access check. |
| `includes/myapi.time_format.inc` | Reused, not duplicated: `myapi_time_format_is_valid()` is the one function in the module that knows the `HH:MM` pattern, and it validates the time half of the status date. |

After adding or modifying any of this, run:

```bash
drush cc all
```

**No `drush updb`.** No field, instance, bundle, table or permission is added
or changed by this feature. `hook_update_N` is not touched.

## The two routes

| Path | Callback | Access callback |
|------|----------|-----------------|
| `node/%node/service-transaction/add` | `myapi_service_transaction_add_page_callback()` | `myapi_service_transaction_add_access()` |
| `node/%node/service-transaction/%node/delete` | `myapi_service_transaction_delete_page_callback()` | `myapi_service_transaction_delete_access()` |

Both are `MENU_CALLBACK` — never visible in a menu — and both carry
`'file' => 'includes/myapi.service_transaction_admin.inc'`. They are only ever
reached from the timeline fieldset.

**There is no edit route of this module's own.** "Editar" points at the native
`node/<transaction_nid>/edit` form of the transaction; all this feature does to
that form is lock `field_request` and force the redirect back.

### `myapi_service_transaction_add_access($node)`

```php
node_access('update', $node) && node_access('create', 'service_transaction')
```

plus `FALSE` for any node that is not a `service_request` — the route is
`node/%node/service-transaction/add` for **any** node id, and this closes it
for every other content type.

### `myapi_service_transaction_delete_access($request_node, $transaction_node)`

Four conditions, and the third is why this function exists instead of reusing
the one above:

1. the first node is a `service_request`;
2. the second is a `service_transaction`;
3. **that transaction belongs to that request** — its `field_request`
   `target_id` equals the request's `nid`;
4. `node_access('update', $request_node)` **and**
   `node_access('delete', $transaction_node)`.

Without condition 3 the route would delete any transaction on the site by
hanging it off a request the operator happens to be able to edit.
`node/<request A>/service-transaction/<transaction of request B>/delete`
answers **403** and deletes nothing.

## Who sees what

Nothing here grants a permission. The operator is `administrator` / `backend`,
and the `administrador edificio` role still does not reach services at all — it
is not in `myapi_building_admin_editable_types()` and this feature does not put
it there.

| Element | Shown when |
|---------|------------|
| The timeline fieldset | The user reached `node/<nid>/edit` of the request, i.e. `node_access('update')` on it |
| "Crear transacción" | Always inside the fieldset; the route re-checks access on click |
| "Editar" (per row) | `node_access('update', $transaction)` |
| "Borrar" (per row) | `node_access('delete', $transaction)` |

Both per-row links are **hidden**, never disabled, for users without access:
the cell is left **empty**, with no substitute text. A link that leads to a 403
is worse than no link.

> **`delete any service_transaction content` is granted to nobody.** No
> `hook_update_N` concedes it — `myapi_building_admin_permissions()` has a unit
> test that fails if any `delete any ...` ever appears there, because the
> module's rule is that content is unpublished or cancelled, not deleted. A
> site that wants `backend` to delete transactions grants it by hand from
> `/admin/people/permissions`. Until then, `backend` sees the "Borrar" column
> empty.

Deciding both links costs one `node_load()` per row. That is accepted over the
low per-request volume: a transaction is a status change, not a chat. Whichever
spec adds a pager decides this too.

## The timeline table

Six columns, one row per **published** (`status = 1`) transaction of the
request:

| Estado | Fecha del estado | Comentario | Autor | Editar | Borrar |
|--------|------------------|------------|-------|--------|--------|

- **Order: `field_status_date` DESC, `nid` DESC.** The `nid` tie-break makes it
  deterministic when two transactions share a minute. This is the **opposite**
  of the order `GET /api/v1/service-requests/{id}` serves (ASC, SPEC 93), on
  purpose: the app narrates the request from beginning to end, the operator
  wants the last thing that happened at the top.
- **Estado** is labelled against `myapi_services_request_statuses()`. A key that
  is not in the catalogue falls back to the raw stored value, which still reads.
- **Fecha del estado** is shown as `AAAA-MM-DD HH:MM`, taken as a **substring**
  of the stored value. It never goes through `strtotime()`:
  `field_status_date` was created with `tz_handling = 'none'` (SPEC 55), so
  what is stored is a naive local time and converting it would shift the hour
  somebody typed by hand. The stored seconds are always `:00`.
- **Autor** is the transaction node's own `uid` — the **operator who saved it**,
  not the requester. An account deleted since shows `Usuario eliminado (#uid)`.
- Empty status, date or comment render as `—`.
- A **despublicada** transaction (`status = 0`) does not appear at all.

The query is this file's own and deliberately **not**
`myapi_service_request_load_transactions()` (SPEC 93): that one lives in
`resources/service_request.resource.inc`, which Regla 5 de CLAUDE.md forbids an
include from entering, and it answers a different question anyway — ASC, no
author, dates already shaped for JSON. Two consumers, two queries.

It carries no `->addTag('node_access')`: whoever reached `node/%nid/edit` of the
request already passed the access check on it, and the transaction has no
access of its own. Per-row access is decided afterwards, and only for the links.

## `field_request_status` of the request is read-only in edit

On `node/<nid>/edit` of a `service_request` the status field is `#disabled`:
visible, with its value, submitted with the form — and impossible to change
from there.

`#disabled` and **not** `#access = FALSE`, deliberately: the operator has to
*see* which status the request is in while deciding which transaction to
create. What they must not do is rewrite it without leaving a trace. The status
moves by creating a transaction, which records who, when and why.

On `node/add/service_request` the field stays **editable**: that form is where
the initial status is chosen, the one SPEC 92's automatic transaction copies.
No timeline fieldset is rendered there either — a request being created has no
history yet.

## Creating a transaction

"Crear transacción" sits at the top of the fieldset and leads to
`node/<nid>/service-transaction/add`, a **plain page** — no modal, no AJAX.
SPEC 57 already tried the jQuery UI Dialog on the claims screen and dropped it.

The form has exactly three fields, all required:

| Field | Element | Notes |
|-------|---------|-------|
| Estado | `select` | `#options` = `myapi_services_request_statuses()`, the six catalogue entries with their labels |
| Fecha del estado | `textfield` | `AAAA-MM-DD HH:MM`, `#default_value` = now. Plain text, **not** `date_select` or `date_popup` — SPEC 57 tried both "combo" widgets live and both broke the alignment of the form with their own CSS |
| Comentario | `textarea` | A transaction without a comment explains nothing |

**There is no field to choose the request**, and no field for the title.
`field_request` travels as a `#type => 'value'` element fixed to the request the
form was opened from; the title is composed by
`myapi_service_transaction_set_title()` (SPEC 92) from `hook_node_presave()`,
which runs inside this form's own `node_save()`.

Validation of the date is `myapi_service_transaction_validate_status_date()`: a
pattern plus `checkdate()` for the date half — so `2026-02-31` fails as loudly
as `ayer` — and `myapi_time_format_is_valid()` for the time half. **A bare date
with no time fails**: the timeline records the exact instant of a status change.

What gets saved:

| Property / field | Value |
|------------------|-------|
| `type` | `service_transaction` |
| `uid` | The **operator who saved**, not the requester |
| `status` | `1` (published) |
| `title` | Autogenerated in `hook_node_presave()` (SPEC 92) |
| `field_request` | `target_id` = the request's `nid` |
| `field_request_status` | The selected status |
| `field_status_date` | The typed value with `:00` appended — `Y-m-d H:i:00` |
| `field_comment` | The typed comment, `value` only, no `format` |

After saving, the browser lands back on `node/<request_nid>/edit`, with the new
transaction as the **first** row.

## Editing a transaction

"Editar" leads to the **native** `node/<transaction_nid>/edit`. Two things are
altered there, and only in edit mode:

- **`field_request` is `#disabled`.** The operator keeps seeing which request
  the transaction belongs to, and Drupal resubmits a disabled element's value,
  so saving never blanks it — nor accepts a different one sent by a
  hand-crafted `POST`, which is the risk this lock exists for. On
  `node/add/service_transaction` the field stays editable.
- **The redirect goes back to the request.**
  `myapi_service_transaction_edit_form_submit_redirect()` reads `field_request`
  off the saved node and sets `$form_state['redirect']` to
  `node/<request_nid>/edit`, so saving lands on the request and not on
  `node/<transaction_nid>`.

The handler is appended to **both** `$form['#submit']` and the Save button's own
`$form['actions']['submit']['#submit']`: `form_execute_handlers()` runs the
triggering element's list when it has one and ignores the form-level one
entirely, and `node_form()` gives its Save button its own. Only one of the two
ever executes.

Editing the status of an existing transaction **also syncs the request**, via
`hook_node_update()` — see below.

## The status sync: transaction → request

`myapi_service_transaction_sync_request_status()` is the delegate of the
`'service_transaction'` branches of **both** `myapi_node_insert()` and
`myapi_node_update()`. Saving a transaction whose `field_request_status`
differs from its request's rewrites the request's own.

```
transaction saved
  → field_request resolves to a service_request?      no  → return
  → transaction has a status?                         no  → return
  → request already in that status?                   yes → return   (no node_save)
  → rewrite field_request_status + node_save($request)
```

The rule lives in the node hooks and not in the creation form's submit
precisely so `node/add/service_transaction` and `node/<nid>/edit` of a
transaction — the native forms, which never go through this feature's creation
page — are covered too, without the sync being written twice.

**It cannot loop.** Three properties, which have to be read together:

1. **The automatic initial transaction fires nothing.** SPEC 92's transaction is
   born copying the status the request already has, so the comparison returns
   before the `node_save()`. Creating a request still writes exactly two nodes.
2. **No cascade.** The `node_save($request)` is an *update* of a
   `service_request`, and `myapi_node_update()` has no `'service_request'`
   branch; the one that does exist, in `myapi_node_insert()`, only runs on
   insert. Whoever adds one must keep that property.
3. **No graph validation.** `myapi_services_request_transitions()` is not
   consulted, so a `closed` → `open` transaction **saves without error**.

That third point reverses SPEC 92's decision knowingly. SPEC 92 left the sync
out because nobody validates the transition graph and syncing would let anyone
put a request into an impossible state. That is still true — and still a
pending spec. What changed is the conclusion: without the sync, "the operator
can change the status" means nothing here, since the transaction would be a log
entry and the real status would have to be moved from a field this screen
locks. And validating the graph **only** here would make this door stricter
than `api/v1`, which does not validate it either. Two doors with different
rules is worse than two doors equally permissive. Whichever spec validates
transitions has to cover both at once.

## Deleting a transaction

"Borrar" leads to `node/<request_nid>/service-transaction/<nid>/delete`, a
confirmation page built with core's `confirm_form()`:

> **¿Borrar esta transacción?**
> Se borrará la transacción «…». Esta acción no se puede deshacer. **El estado
> de la solicitud no cambia.**

- **Cancelar** returns to `node/<request_nid>/edit` and deletes nothing.
- **Borrar** calls `node_delete()` and returns to `node/<request_nid>/edit`,
  without the row.

This is the first node deletion the module offers, which is why it carries an
explicit confirmation and its own route: core's `node/<nid>/delete` deletes
correctly but leaves the operator on the front page, outside the request they
came from.

**Deleting does not rewind the status.** The request's `field_request_status`
stays exactly where it was, even when the deleted transaction is the one that
put it there. Recalculating it from the most recent surviving transaction would
turn deletion into a second way of changing the status — invisible, with no
author and no comment — and would force a decision about which status is left
when no transaction survives at all. Deleting corrects the log; changing the
status is done by creating a transaction. The confirmation text says so out
loud, because it is precisely what an operator could assume the other way
round.

**The automatic initial transaction of SPEC 92 is deleted like any other.**
Nothing distinguishes it today: protecting it would need either a new field or
the guess that it is the one with the lowest `nid`, a heuristic that breaks the
moment somebody deletes it and the next one inherits the post.

## What this feature does **not** do

Each of these is a spec of its own if it is ever wanted:

- **No listing.** `admin/content/service-requests`, with its filters and its own
  per-role access decision, does not exist.
- **No transition validation.** See the sync section above. When it arrives it
  must cover this screen *and* the `api/v1` endpoints, not one door.
- **No new permission.** `administrador edificio` still does not reach
  services, and `backend` is not granted `delete any service_transaction
  content`.
- **No notification.** The marketplace has no notifier yet. When it gets one,
  that spec decides whether these transactions fire it.
- **No API change.** `GET /api/v1/service-requests/{id}` already serves the
  timeline since SPEC 93 and returns whatever the operator writes, edits or
  deletes here — in ascending order, with no line changed in
  `resources/service_request.resource.inc`.
- **No attachments.** `service_transaction` has no image or file fields, unlike
  `claim_transaction`, and this feature does not add them.
- **No pager.** Low volume assumed, same as SPEC 57.
- **No audit.** Who edited or deleted what is not recorded; the bundle has no
  revisions and none are enabled.
- **No cascade delete.** Deleting a request does not delete its transactions,
  and nothing here deletes anything but the single transaction confirmed.
