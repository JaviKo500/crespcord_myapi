# Initial transaction of a service request (automatic)

Every `service_request` is born with the first entry of its timeline: one
`service_transaction` node that copies the status the request was created
with, and carries an acknowledgement comment and an autogenerated title
(SPEC 92).

**This is not an API endpoint.** No route is added, no response changes, and
nothing under `resources/` calls into it. The trigger is `hook_node_insert()`,
so it covers every creation path with a single implementation:

| Path | Covered |
|------|---------|
| `node/add/service_request` (back office) | yes |
| `POST /api/v1/service-requests` (SPEC 90) | yes |
| Any future programmatic `node_save()` (migration, another resource) | yes |

It depends on SPEC 77 (the `service_transaction` bundle, its four fields and
the `myapi_services_request_statuses()` catalogue) and SPEC 87 (`direct`, the
second status a request can be born in, which is why the acknowledgement has
two first-person texts and not one).

---

## Files

| File | Role |
|------|------|
| `myapi.module` | Glue only, two branches: `'service_request'` in `myapi_node_insert()` (creates the transaction) and `'service_transaction'` in `myapi_node_presave()` (writes the title). Three lines each, both delegating. |
| `includes/myapi.service_transaction.inc` | Everything else: the two constants, the three acknowledgement texts, the title composition, and the two hook delegates. Loaded with `module_load_include()` from `myapi.module`. |
| `includes/myapi.services_common.inc` | Reused, not duplicated: `myapi_services_request_statuses()` is the single source of the status labels, the same one `myapi.install` reads to build `field_request_status`' `allowed_values`. |
| `includes/myapi.building_admin.inc` | Reused, not duplicated: `myapi_building_admin_field_value()` / `_field_target_id()` (SPEC 49) read the request's fields. |

After adding this, run:

```bash
drush cc all
```

**No `drush updb`.** No field, instance, bundle, table or permission is added
or changed — the bundle and its four fields have existed untouched since
SPEC 77, and this is simply the first code that writes into them.

## The node that gets created

| Property / field | Value |
|------------------|-------|
| `type` | `service_transaction` |
| `uid` | The `uid` of the request just inserted — the resident behind the token via the API, the operator via the back office |
| `status` | `1` (published) |
| `title` | Autogenerated in `hook_node_presave()` — see below |
| `field_request` | `target_id` = the request's `nid` |
| `field_request_status` | Copied verbatim from the request's `field_request_status` |
| `field_status_date` | `date('Y-m-d H:i:00')` — the real instant of the creation, seconds pinned |
| `field_comment` | The acknowledgement text, `value` only, no `format` |

Two things worth stating about that table:

- **"According to the status" means copy, not filter.** Exactly one transaction
  is always created, whatever the status. The status decides *what is recorded*
  and *which text it carries*, never *whether* the row exists — a request an
  operator registers already closed is the one that most needs a trace of why.
- **`field_status_date` is minute-granularity, not a day.** The field is
  `datetime` (shared with `claim_transaction`), so the string is written, not a
  timestamp. Midnight was the exact bug SPEC 58 had to fix in claims.

## The three acknowledgement texts

`myapi_service_transaction_initial_comment($status)`:

| Birth status | Text |
|--------------|------|
| `open` | Hemos recibido su solicitud. Los proveedores de la categoría podrán enviarle ofertas y se le notificará cualquier novedad. |
| `direct` | Hemos recibido su solicitud y fue enviada al proveedor seleccionado. Se le notificará cualquier novedad. |
| `offered`, `assigned`, `closed`, `cancelled`, or any unknown key | Solicitud registrada con estado `@estado`. |
| `NULL` or `''` | Solicitud registrada. |

- `@estado` is the **label** from `myapi_services_request_statuses()` («Con
  ofertas», «Asignada», «Cerrada», «Cancelada»), or the raw key when the key is
  not in the catalogue. An unknown status degrades to a text that still reads —
  never to a commentless transaction.
- Renaming a label in that catalogue changes the text with no edit to
  `includes/myapi.service_transaction.inc`. This is a **deliberate divergence**
  from `myapi_claim_transaction_initial_comment()`, which transcribes its noun
  by hand: there the labels are `allowed_values` an administrator can edit from
  the browser and would rewrite the sentence mid-phrase; here the catalogue
  lives in code. The underlying rule is the same in both — the label's source is
  the one that cannot change under the sentence's feet.
- Only `open` and `direct` address the resident in the first person. The rest
  describe an administrative record, which is exactly what they are.
- The texts go through `t()`, not `myapi_t()`: they are read by the operator in
  the back office and travel in no API response. See the "what this does not do"
  section below.

## The autogenerated title

`myapi_service_transaction_title()`, four segments joined by ` · `:

```
Solicitud #412 · Abierta · 19/08/2026 14:30 · Hemos recibido su solicitud. Los…
```

- **Each segment is omitted when its value is missing**, with no dangling
  separator at the start, in the middle or at the end. With nothing resolvable
  at all the title is `Transacción de solicitud` — the promise that a
  transaction is never titleless again.
- The date renders `d/m/Y H:i` through `strtotime()`: an unparseable value
  **drops the segment** instead of printing `01/01/1970`.
- The comment is collapsed to one line (newlines and runs of spaces to a single
  space) and truncated to **60** characters with `truncate_utf8($wordsafe,
  $add_ellipsis)`, so the cut lands on a word boundary and ends in `…`.
- The whole title is truncated to **255** (`node.title` is `varchar(255)`), so
  PHP makes the cut on a UTF-8 character boundary instead of MySQL doing it
  mid-character.
- Nothing is escaped here: `node.title` is stored raw and Drupal escapes it at
  render time.

The title is written in `hook_node_presave()`, which means it covers
transactions created **by hand** from `node/add/service_transaction` too, and
that it is **regenerated on every edition**. It is therefore not a stable
identifier — the `nid` is. A title describing something the transaction no
longer is would be worse.

| Constant | Value |
|----------|-------|
| `MYAPI_SERVICE_TRANSACTION_TITLE_COMMENT_LENGTH` | `60` |
| `MYAPI_SERVICE_TRANSACTION_TITLE_MAX_LENGTH` | `255` |

Both are this file's own and deliberately **not** shared with
`claim_transaction`'s: reusing those would force this include to load the whole
claims one to read two numbers, and would tie together the title length of two
features that can diverge.

## What this behaviour does **not** do

Four explicit non-behaviours, each one a spec of its own if it is ever wanted:

- **It does not react to editions.** Changing a request's status, title or
  description from `node/%nid/edit` creates **no** new transaction. Only
  `hook_node_insert()` is implemented, never `hook_node_update()`. Each status
  transition (offering, assigning, closing, cancelling) will create its own
  transaction in its own spec, next to the rest of its effects.
- ~~**It does not sync backwards.**~~ **Superseded by SPEC 94.** Saving a
  `service_transaction` with a different status now **does** rewrite its
  request's `field_request_status`, through
  `myapi_service_transaction_sync_request_status()`
  (`includes/myapi.service_transaction_admin.inc`). The reason given here for
  leaving it out — the transition graph `myapi_services_request_transitions()`
  exists and nobody validates it — is still true and still a pending spec;
  what changed is the conclusion drawn from it. See
  [`service-transaction-timeline.md`](service-transaction-timeline.md).
- ~~**It is not exposed in the API.**~~ **Superseded by SPEC 93.**
  `GET /api/v1/service-requests/{id}` serves the timeline under a
  `transactions` key, in ascending order. The listing and the `201` of
  `POST /api/v1/service-requests` are still byte for byte what they were.
- **It does not notify.** No email, no push, no notification row. The
  marketplace has no notifier at all yet, which is also why there is no
  transient skip flag here — there is nothing to silence.

Two more, worth writing down:

- **No backfill.** Requests created before this change keep no transaction. The
  hook only runs on an `INSERT`, and an invented row would carry an
  acknowledgement nobody ever issued, next to a status that is the *current*
  one and not the one it was born with.
- ~~**No back-office timeline table.**~~ **Superseded by SPEC 94.**
  `node/%nid/edit` of a request now carries a timeline fieldset with a "Crear
  transacción" link and per-row "Editar" / "Borrar" actions, and the request's
  own `field_request_status` is read-only there. All of it lives in
  `includes/myapi.service_transaction_admin.inc` and is documented in
  [`service-transaction-timeline.md`](service-transaction-timeline.md); this
  file and its behaviour are unchanged by it.

## Two things to be careful with

**`field_request` is shared.** Both `service_offer` and `service_transaction`
point at a request through `field_request` (SPEC 77). Until this spec that
column only ever held offers, so a query that forgot to filter by bundle got
the right answer by accident. It no longer does: **any query on
`field_data_field_request` must filter by `bundle`**, or `offers_count` starts
counting transactions as offers. The filter already exists in
`myapi_service_request_base_query()` and in the detail (SPEC 88/89), and
`ServiceRequestListEndpointTest` / `ServiceRequestDetailEndpointTest` already
seed a `service_transaction` on purpose to prove it is excluded.

**A failure here aborts the request.** `node_save()` runs inside a database
transaction and `hook_node_insert()` runs within it, so an exception while
saving the transaction takes the request down with it and the `POST` answers a
bare 500. This is accepted on purpose and **not** wrapped in a `try/catch`,
which would leave requests silently without a transaction — worse than failing
loudly. The creator writes four fields that have existed since SPEC 77 and does
no external I/O of any kind, so its failure surface is the same as the
`node_save()` that already ran. Claims have carried the identical risk since
SPEC 57 without an incident.

**An entry no longer implies a status change.** *One entry per status change*
was true from SPEC 77 until SPEC 101, which relaxes it in **exactly one case**:
when the awarded provider of a `direct` request
[sends their quote](service-offer.md#quoting-a-direct-request), an entry is
written whose `field_request_status` **repeats** the `direct` the request
already carried, because the status genuinely did not move. It is written
anyway so the resident sees *"your provider sent you a quote"* on their
timeline. What tells that entry from the acknowledgement above it is the
**`field_comment`**, not the status — so a client that renders the status key as
the headline will print *Directa* twice. Render the comment; treat the status as
data. Nothing else in the module writes an entry without a transition behind it.

**No cascade, and how to keep it that way.** Inserting the transaction fires
`hook_node_insert()` again with a `service_transaction` node. There is
deliberately **no branch for that bundle** in that hook, so it matches nothing
and stops. If a future spec adds one, it must not re-save the request from it —
that is what would make the cascade infinite. A unit test guards the absence.

## Tests

`tests/unit/ServiceTransactionTest.php` covers the pure half: the three
acknowledgement texts including the unknown-key and absent-status fallbacks,
the label being read from the catalogue rather than transcribed, every dropped
title segment, the unparseable date, the comment collapse and its 60-character
cut, and the 255 ceiling.

The two Field API functions (`_set_title()` and `_create_initial()`) are not
unit-tested — they are Field API plus the database, which `tests/unit` avoids —
but three guards read `myapi.module` as text and fail if either hook branch
disappears, or if a `service_transaction` branch ever appears in
`hook_node_insert()`.
